## Performance evidence

Same browser, synthetic fixtures, no external assets:

| Operation | v3.5.0 | Proposed v3.6.0 |
| --- | --- | --- |
| prepareCaptureClone, median of 5 calls, ~4,800 nodes | 81.1 ms | 54.1 ms |
| Complete 2× lossless A4 PDF, median of 3 alternating runs | 1,588.5 ms | 1,559.2 ms |
| PDF output in that fixture | 5 pages / 1,820,111 bytes | 5 pages / 1,820,111 bytes |

Preprocessing fixture: 1,200 24px rows, each with three spans, and a fixed two-button toolbar; execute prepareCaptureClone on the document. PDF fixture: 160 24px paragraphs, 600×3,840 CSS pixels, white background, A4 margins 12/12/10/10 mm; serialize actual PDF bytes instead of downloading. All timing samples are in the JSON record.

The preprocessing reduction is about 33%. Same-quality total PDF time differs by only about 2%, with overlapping samples; **no general end-to-end speedup is established**. The async encoding path primarily removes synchronous base64 work and gives the UI execution time between pages. Higher responsiveness does not imply faster rendering.

The 2× preset has 44% of the pixel count of 3×; 1.5× has 25%. This is pixel arithmetic, not an export-time promise. Existing user preferences are preserved. Fast mode changes both resolution and PDF encoding, and therefore trades detail for processing cost.

## Cancellation contract

Cancel/Esc sets a request flag. Active html2canvas work is allowed to settle; the job then skips downstream encoding/download and restores scroll, clone state and controls. Single html2canvas/jsPDF calls remain non-interruptible. Stage bars are not predicted percentages of elapsed time. Selection remains available after cancellation or errors.
